# HF-01B Design Handoff

Date: 2026-08-30
Status: design resolved; [implementation ticket](../plans/2026-08-30-harness-first/HF-01B-host-memory-context.md) accepted by Sol Ultra for Luna Max coding.
Product code baseline: `25e70a94811c41cf3ebb9a2a0cae1e1b019ddc41`.
Goal: [HF-GOAL-1.0](../../product/anna-harness-first-goal-2026-08-30.md).
Design roles: Luna Max and independent Sol Ultra review.

## Confirmed Constraints

- `MemoryRepository.retrieve({runId})` checks that the Run started, allocates
  a Run-stream seq and appends `memory.hit` directly. Pi also owns a local seq.
  Calling this unmodified from a started callback creates two writers.
- Pi currently treats persisted `run.started` as evidence of restoration,
  even if there is no transcript. A crash before hydration completes must not
  bypass the required loader or enter an invalid continuation.
- `memory.hit` carries provenance, not a recoverable copy of the model input.
  Transient Memory text alone is insufficient to prove unchanged restoration.
- Preserve the original admitted goal/Profile, fingerprint checks, transcript,
  cumulative budget and `sink.read`. A lookup failure cannot become zero-hit.

## Options Considered

Luna proposed one per-Run writer in `DurableRunRuntime`, shared by Memory,
Kernel and Eval. Sol proposed retaining the existing serial handoff from
Runtime queued to Pi active events to Eval, with the Host returning prepared
context and hit drafts; active-stage canonical appends would remain in Pi.

Select one explicit authority after checking the actual `RunContext` and
EventSink contracts. Do not combine both seq allocators, conceal offsets or
relax Store validation. A new writer abstraction requires evidence that the
broader contract change is necessary for this slice.

Decision: retain the existing serial stage handoff for this ticket. The Host
commits a private scoped prepared-input projection; Pi's active appender emits
hit/readiness events. SQLite sequencing and the shared EventSink remain
unchanged. Sol accepted the current projection CAS API as sufficient for this
contract. The implementation ticket records crash and old-history boundaries.

In either option the Host owns scoped accepted-Memory retrieval. The adapter
only consumes normalized untrusted context. Define an immutable, recoverable
input projection/readiness record, including a successful zero-hit lookup,
before using a persisted start as a continuation boundary. Do not silently
rehydrate changed Memory into an original fingerprint on restore.

## Required Public RED Cases

1. Actual Pi and real SQLite: block the Host loader; model call count remains
   zero. Release it and observe started, hits, first model, contiguous seq,
   required Eval and one terminal in the correct order.
2. Store/scope/policy/loading-receipt failure invokes zero model calls.
   Legitimate zero-hit continues; `read:none` does not call the repository.
   Empty/tokenless queries cannot retrieve every accepted record.
3. Crash after started, during hit persistence and after input/transcript
   persistence. Reopen SQLite without missed/double hydration or tool replay;
   preserve the original context/fingerprint and cumulative usage/budgets.
4. Accepted Memory survives restart and is usable by a new authorized Run;
   candidates, deleted/revoked and unauthorized cross-Channel records do not
   become usable context. Hit events expose provenance, not raw Memory text.
